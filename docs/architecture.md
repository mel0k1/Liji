# Архитектура Liji

Liji строится как слоёная система, где каждый слой имеет чёткий контракт. Ниже — разбор всех уровней, принципы урезания Fuchsia и стратегия сборки.

## Общая схема

```
┌────────────────────────────────────────────────────────────┐
│                        Mejo DE                             │
│  Mejo shell · launcher · панель · переключатель окон       │
│  настройки · системный трей · виджеты · экран блокировки   │
├────────────────────────────────────────────────────────────┤
│                Flutter Engine (Impeller)                   │
│        Dart VM · flutter runner · Vulkan-рендер            │
├────────────────────────────────────────────────────────────┤
│                  Fuchsia core (урезанный)                  │
│  Component Framework (CFv2) · FIDL · appmgr-преемники      │
│  Scenic (композитор) · input pipeline · аудио              │
│  netstack3 · файловые системы (minfs/blobfs/fxfs)          │
│  pkg-cache · pkg-resolver · fshost · driver manager        │
├────────────────────────────────────────────────────────────┤
│                        Zircon                              │
│  планировщик · vmo · порты · каналы · capability-права     │
│  пользовательские драйверы · vDSO · boot protocol          │
└────────────────────────────────────────────────────────────┘
```

## Слой 1 — Zircon

Zircon — микроядро, управляющее процессами, памятью (VMO), планированием и IPC. Ключевое отличие от классических ядер — **capability-модель**: процесс не имеет «прав по умолчанию»; каждый доступ к объекту (канал, VMO, порт, задача) выражается дескриптором-ручкой (handle), который кто-то явно передал. Для Liji это фундамент безопасности: Mejo и приложения не могут «подсмотреть» друг у друга память или файлы — только то, что им выдал компонентный фреймворк.

Драйверы в Zircon живут в пользовательском пространстве (DFv2): упавший драйвер GPU не уносит систему, а перезапускается. Для десктопа, где зоопарк железа неизбежен, это критично: одна кривая периферия не роняет ядро.

## Слой 2 — Fuchsia core

Из платформы Fuchsia мы сохраняем минимально достаточное ядро платформы, чтобы Liji оставалась **настоящей ОС**, а не демонстрационным стендом:

- **Component Framework (CFv2)** — сердце системы: всё, от shell до браузера, является компонентом с манифестом и песочницей. Mejo тоже будет компонентом — со своими правами и маршрутами FIDL.
- **FIDL** — единый IPC-язык системы. Контракты между Mejo и системными сервисами (сеть, звук, питание, Bluetooth в будущем) описываются FIDL-протоколами.
- **Scenic** — системный композитор. Flutter-движок рендерит свои слои и отдаёт их Scenic; окна Mejo — это композиция слоёв нескольких процессов.
- **Подсистемы**: ввод (input pipeline), аудио (Audio Core), сеть (netstack3), файловые системы (fxfs/blobfs/minfs), менеджер пакетов (pkg-cache/pkg-resolver — база для установки приложений и обновлений).

Из этого слоя вырезаются: сэмплы и демо, экспериментальные сессии и оболочки (Ermine/Workstation-наследие — их место занимает Mejo), деревья тестов, невостребованные продукты и платы, доки исходников.

## Слой 3 — Flutter Engine и Mejo

Flutter на Fuchsia работает через **flutter runner** — компонент, линкующий Flutter Engine против Zircon/Scenic напрямую. Никакого X11, Wayland или промежуточного GTK: Dart-код Mejo рендерится Impeller'ом в Vulkan-текстуры и композируется Scenic'ом.

**Mejo** состоит из модулей (все — Dart-пакеты в будущих репозиториях/директориях):

| Модуль | Назначение |
|---|---|
| `mejo_shell` | Корневой компонент сессии: запуск системных сервисов DE, роутинг |
| `mejo_launcher` | Лаунчер приложений, поиск, сетка в духе M3E |
| `mejo_panel` | Системная панель: часы, трей, индикаторы, шторка настроек |
| `mejo_wm` | Компоновка окон: тайлинг/флоат, анимации контейнеров M3E |
| `mejo_kit` | Дизайн-система M3E: темы, цвет, типографика, формы, motion |

Приложения Liji — обычные Fuchsia-компоненты с flutter runner, устанавливаемые как пакеты (`.far`). Mejo обнаруживает их через component resolver и лаунчер.

## Стратегия урезания исходников

Урезание работает на трёх уровнях, от самого надёжного к самому грубому:

1. **Манифест jiri.** Полная выкачка (`flower`) тянет все перталсы. Лёгкий `stem` тянет только платформенный репозиторий fuchsia + cobalt + prebuilts. Скрипт `fetch_fuchsia.sh` по умолчанию использует `stem`.
2. **Продуктовая конфигурация.** `fx set core.x64` собирает строго то, что входит в продукт. Наша цель — собственный продукт `liji.x64`, базирующийся на `core`, где базовый набор (`//build/bundles` + Mejo) описан декларативно.
3. **Обрезка дерева.** `prune_fuchsia.sh` удаляет заведомо ненужные каталоги (сэмплы, исходные доки, тяжёлые тестовые деревья) для экономии диска. Это чисто утилитарная мера: GN и так не компилирует лишнее, а `jiri update` после обрезки вернёт удалённое — запускать обрезку стоит после фиксации выкачки.

## Стратегия сборки

Этапы (детали — в roadmap):

1. Выкачанный checkout собирается штатным инструментарием: `fx set core.x64 --release && fx build`.
2. Образ запускается в QEMU/FEMU (`fx emu`), KVM ускоряет.
3. В образ добавляется flutter runner и первый Mejo-компонент.
4. Появляется собственный продукт `liji` (GN-определение), где сессией по умолчанию становится Mejo, а не стандартная сессия Fuchsia.
5. Отдельная ветка работ — продукт `bringup`-уровня для реального железа x64 (UEFI-загрузка, минимальные драйверы).

## Риски и их обработка

- **Драйверы реального железа** — главная зона риска. Обходной путь: сначала QEMU (драйверы известны), затем ограниченный белый список железа x64.
- **Flutter на Fuchsia развивается в рваном ритме** — фиксируемся на проверенных ревизиях flutter runner из выкачки, апгрейдим осознанно.
- **Объём сборки** — лечится связкой `stem` + prune + `core`-продукт; дисковый бюджет сборки — 80–90 ГБ, планировать сразу.
